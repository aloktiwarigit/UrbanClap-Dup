## Round 1 — 1 P1, 1 P2

**[P1] Send an ISO datetime for hold overrides** — `admin-web/src/components/commissions/HoldOverrideDialog.tsx:43`
The component forwarded the raw `<input type="date">` value (`YYYY-MM-DD`) to `setHoldOverride`,
but the API validates `until` as `z.string().datetime()`
(`api/src/schemas/commission-ledger.ts:77`). Every save 400'd, so a super-admin could never place
a hold override — the feature had never worked.

*Why eleven internal reviews missed it:* the component tests mock `setHoldOverride`, and a mock
accepts any string; the API tests feed the handler valid ISO input. Nobody exercised the seam
between them. This is the third seam defect on this branch and the clearest argument for the
cross-model gate.

**Fixed** in `c9bfffc2`: a new pure helper `endOfIstDayUtcIso` converts the selected date to
**end of that day in IST, expressed as UTC** — `2026-09-30` → `2026-09-30T18:29:59.999Z`. End-of-day
IST rather than UTC midnight because the business is in Ayodhya (UTC+5:30): an override "until
30 September" must cover all of 30 September there, and a naive UTC conversion would have expired
it at 05:30 IST that morning. Empty dates are now rejected client-side in both locales. The
shape-blind `toHaveBeenCalledWith({until: '2026-09-30'})` assertion — the one that let this ship —
was replaced with a test asserting the emitted value round-trips as a real ISO datetime.

**[P2] Wait for payout status before showing the queue** — `admin-web/src/components/finance/FinanceClient.tsx:165`
The queue rendered when `summary?.payoutsEnabled !== false`, which is true while `summary` is still
`null`. If the queue request resolved before the summary, the operator briefly saw the queue and
its approve controls in a cash-only pilot before `payoutsEnabled: false` arrived.

**Fixed** in `c9bfffc2`: a null summary is treated as *loading*, not as permission. Test added for
the interleaving where the queue resolves first.
