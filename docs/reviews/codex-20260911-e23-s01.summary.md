# Codex review — E23-S01 (weekly incentive milestones)

**Base:** `main`. Two rounds, per project policy (one re-run after a fix, then stop iterating).

## Round 1 — reviewed at `8339380` (post smoke-gate fixture fix), fixed in `49d5823a`

1. **[P2] `GET /v1/config/technician` 502s every technician on a partial admin write.**
   The existing (pre-E23-S01) endpoint read the incentive config via the raw,
   non-defaulting `systemDocsRepo.getIncentiveConfig()`. A `PUT {"enabled":true}` before
   milestones/capFractionBps were ever set produced a stored doc missing required fields;
   the response schema requires all three, so every technician's config fetch failed.
   Fixed: consume `getEffectiveIncentiveConfig()` instead (already per-field-defaults,
   never returns a partial shape).
2. **[P2] `GET /v1/technicians/me/incentives` projects a bonus for a disabled programme.**
   `nextMilestone`/`projectedBonusPaise`/`projectedCapPaise` were computed against
   `cfg.milestones` unconditionally, even when `cfg.enabled` is false. An admin who
   disables the programme after configuring real milestones leaves a technician seeing
   progress toward a bonus the weekly run will never award. Fixed: zero the projection
   and omit `nextMilestone` when disabled; factual counts (`countedJobs`,
   `countedCommissionPaise`) are unaffected.

Both proven non-vacuous by reverting each fix (`git stash`) and confirming its named
regression test fails without it.

## Round 2 — reviewed at `49d5823a`, fixed in `752b880c`

3. **[P2] A manual rerun does not repair a stale award on replay.** `applyAward`'s
   `REPLAYED` branch returned before reaching the `reconcileAwardApplied` call further
   down — so a rerun (the runbook's own documented recovery for a partial failure) never
   repaired `appliedPaise`/`status` left stale by an earlier failed reconcile or a later
   credit consumption. Fixed: reconcile (same best-effort try/catch as the `AWARDED`
   path) before returning `REPLAYED`.
4. **[P3] A nonexistent ISO week reads as a server failure.** `2027-W53` matches the
   `IST_WEEK_KEY_RE` regex but 2027 has no 53rd week; `istWeekBounds` throws, and the
   throw fell into the generic upstream-error catch — 502/Sentry-captured, indistinguishable
   from a real Cosmos failure, for what is a client input mistake. Fixed: validate with
   `istWeekBounds` before entering the run.

Both proven non-vacuous the same way.

Full smoke gate green after both rounds: 238 files / 2375 tests, `tsc --noEmit -p
tsconfig.tests.json` clean.

Not re-reviewed a third time — findings across two rounds were real and fixed; per
project policy, further Codex rounds are not spent chasing marginal residuals.
