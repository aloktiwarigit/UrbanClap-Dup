# ADR-0035: Weekly technician incentives are credit-only, capped as a fraction of generated commission, and the cap does not fully close the margin-gaming case at its shipped setting

- **Status:** accepted
- **Date:** 2026-09-10
- **Deciders:** Alok Tiwari (owner), implementing session (E23-S01)

## Context

Owner requirement R5 asks for a weekly milestone bonus that rewards technicians for completing
more jobs in a week — e.g. "10 jobs in a week earns a ₹300 bonus." Two constraints shape how that
bonus can be paid:

1. **The ₹0 pilot has no cash payout rail for a bonus.** Technician earnings already settle via
   Razorpay Route on a per-job basis; adding a second, out-of-band cash transfer for incentives
   would require its own reconciliation, its own failure handling, and its own audit trail — real
   infrastructure this pilot's budget does not have (`docs/architecture.md` — ₹0/month operational
   floor).
2. **A cash bonus lets a technician profit from self-booking.** If the bonus pays cash and a
   technician can create or influence bookings assigned to themselves (directly, or via a
   confederate), a milestone bonus becomes a way to manufacture free money rather than reward real
   work — the same class of risk the commission-ledger work (ADR-0031, ADR-0032) already treats as
   a first-class threat to the platform's revenue.

A bonus that is **credit against commission owed** sidesteps both constraints: it needs no new
payout rail (it reduces what the technician already owes through the existing E21-S02 commission
ledger), and it cannot be extracted as cash even by a technician who successfully games the job
count, because the technician never receives money — only a reduction in what they owe.

That still leaves an economic question this ADR must answer honestly: crediting a bonus against
commission does not, by itself, prevent someone from gaming the *count* of jobs that earns the
bonus. Cheap, low-effort "phantom" bookings could pad the job count toward a milestone. The design
needed an anti-gaming guard on the counting rule itself, not just a payment-rail constraint — and
Task 5's tests found that guard's shipped configuration does not fully close the strongest version
of that attack (see Consequence 1 below).

## Decision

The weekly incentive award is **credit-only**, computed and applied as follows:

- **Counting rule (spec §7.8).** A receivable counts toward the week's job count and commission
  base when its `createdAt` falls inside the IST week **and** `bookingAmount >=
  minCountableBookingPaise` (default ₹249 — the cheapest real service at pilot pricing, so a
  "booking" cheaper than the cheapest real service cannot pad the count). `WAIVED` receivables
  still count — the technician did the job; an admin's decision to forgive the commission
  afterwards is a separate, unrelated fact.
- **Milestone lookup.** `computeWeek` (`api/src/services/incentive.service.ts`) finds the highest
  milestone whose `jobs` threshold the counted job count reaches, in an admin-configured,
  strictly-ascending (in both `jobs` and `bonusPaise`) milestone table.
- **The cap.** The gross bonus at that milestone is capped at `capFractionBps` of
  `countedCommissionPaise` — the commission actually generated by the counted jobs that week —
  floored, never rounded, so the platform can never over-credit by a rounding paisa. Default
  `capFractionBps = 6000` (60%), admin-editable via `PUT /v1/admin/incentives/config`.
  `awardedPaise = min(grossBonusPaise, capPaise)`. A zero award is never written at all — no
  document, no audit entry, no P&L line.
- **Anchor + allocator, not a new payment path.** The award document
  (`docType: 'INCENTIVE_AWARD'`, `id: inc:${technicianId}:${weekKey}`) lives in the **existing**
  `commission_receivables` container (partition `/technicianId`), discriminated by `docType`
  alongside the existing `RECEIVABLE`/`REMITTANCE`/`CREDIT` docs, and is handed to the **existing**
  E21-S02 `applyCredit` allocator as its `anchor`. The whole award — create the award doc, replace
  each allocated receivable under its `_etag`, optionally create a leftover `CREDIT` — is one
  single-partition Cosmos `TransactionalBatch`. This gives idempotent replay (the deterministic
  award id 409s on op 0 before any row is touched), atomicity (all-or-nothing), and concurrency
  safety (a row moving under the batch surfaces as a 412 and the allocator re-plans) for free,
  rather than reimplementing any of the three in a bespoke incentive-payment path.
- **Snapshotting.** `milestoneSnapshot`, `capFractionBpsSnapshot`, and
  `minCountableBookingPaiseSnapshot` are copied onto every award at award time (spec §3.5), so a
  later admin edit to the live config can never re-price a week that has already been awarded.
- **Credit-only, enforced in three independent layers**, not by convention alone:
  1. `IncentiveAwardWriteSchema` (`api/src/schemas/incentive.ts`) is `.strict()` at every level
     (top-level and nested inside `milestoneSnapshot`/`reachedMilestone`) — a `payoutPaise`,
     `netPayable`, or `razorpayTransferId` field added in a future edit throws at parse time and
     can never reach Cosmos. Only `incentive.service.ts` calls this schema.
  2. A static Vitest test (`api/tests/static/incentives-credit-only.test.ts`) scans the incentive
     module and the award schema for payout-shaped identifiers, and scans every payout/settlement
     file for incentive identifiers — proved (Task 17) to fail on all three of a value-position
     declaration, a type-position reference, and an object-literal key injected into the real
     files, each independently reverted afterward.
  3. Two Semgrep rules in `api/.semgrep.yml` (`incentives-credit-only`,
     `incentives-not-in-payout-path`) — proved against real Semgrep (via Docker, since the native
     CLI is blocked by this environment's Application Control policy) to catch all three of the
     same injected shapes, with 0 false positives against the clean tree including the schema
     file's own doc comment that names these tokens in prose.

## Consequences

State these four plainly — this is the durable record of what the anti-gaming design actually
achieves, not an aspirational description of it:

1. **The shipped 6000 bps (60%) cap does NOT close the strongest margin-gaming case.** Task 5's
   `PROOF` test prices a technician who does 7 real ₹1,000 jobs and pads the count to the 10-job
   milestone with 3 cheap ₹249 jobs: `countedCommissionPaise` = 170,434 paise, `capPaise` =
   `floor(170434 × 0.60)` = 102,260 paise — far above the 30,000-paise gross bonus, so the cap
   never bites and the technician receives the full 30,000-paise bonus. Net to the technician
   after "spending" 16,434 paise of real commission on the 3 padding jobs: **+13,566 paise of pure
   profit from gaming the count.** The shipped cap does close the cheaper, all-fake variant of the
   same attack (10 fake ₹249 jobs nets a bonus of only 16,434 paise against a 30,000-paise gross
   bonus — the cap bites there). **A lower cap, 1500 bps (15%), closes the 7-real-plus-3-cheap
   case with no false positive on ten genuine ₹1,000 jobs** (Task 5 `PROOF`: at 1500 bps the mixed
   attack's `capPaise` = 25,565, below the 30,000 gross bonus, so the technician is capped below
   their padding cost and gains nothing; ten genuine jobs still clear the cap comfortably at
   33,000 vs. a 30,000 gross bonus, so an honest week is untouched). **The lever is one admin
   config value** (`capFractionBps`, `PUT /v1/admin/incentives/config`) — no code change is needed
   to close the gap, but at the setting this story ships with, it is open. Do not claim, here or
   anywhere else, that the cap makes gaming the milestone count impossible; it demonstrably does
   not, at the default, for a technician willing to mix in a minority of cheap jobs.
2. **`appliedPaise` is reconciled from allocations carrying TWO different `refId` values, not
   one.** Spec §5.5 describes "allocations with `refId = awardId`"; that undercounts. When an
   award cannot be fully allocated against outstanding receivables in the same batch, the
   remainder becomes a `CREDIT` document with id `cr:${awardId}` (`creditDocId`), and a later
   `consumePendingCredits` run stamps the allocations it writes against that credit's id, not the
   award's id. `reconcileAwardApplied` (`incentive.service.ts`) therefore sums allocations whose
   `refId` matches **either** `awardId` **or** `cr:${awardId}`. Counting only the award id leaves
   a bonus that was eventually fully delivered reading `PARTIAL` forever. Spec §5.5's
   single-`refId` wording is wrong; this ADR is the correction of record.
3. **Re-running a week after a config edit is a no-op, not a re-price.** The allocator's anchor
   `matches` predicate compares only `(technicianId, weekKey)` — deliberately not the awarded
   amount. `awardedPaise` is a function of the config in effect at award time (via the snapshot),
   so a later edit to `capFractionBps` or the milestone table and a subsequent re-run for the same
   week must return `REPLAYED`, never a second, differently-priced award for the same week. This
   is why the allocator's fail-closed default (which normally demands the existing anchor's stored
   amount match the incoming one) is deliberately overridden here.
4. **The owner P&L's incentive-cost line — like every other line in it — is bucketed by raw UTC
   calendar day, not IST, even though spec §7.8 asks for IST-day bucketing.** This was not the
   original plan: the first implementation of `getDailyPnL`'s incentive line called
   `incentiveRepo.sumAppliedByIstDay` (genuinely IST-bucketed, per spec), while the pre-existing
   booking loop in the same function buckets by raw UTC day (`completedAt.slice(0, 10)`) and was
   out of scope to change (re-bucketing it to IST would move every historical P&L number). Review
   caught that mismatch as a real bug, not a rounding nit: for any award `computedAt` between
   18:30 and 23:59:59.999 UTC, the IST calendar day is already the next day, so the two maps'
   date-string keys silently diverged and misattributed that window's incentive cost to the wrong
   day-row. The fix conformed the incentive line to the booking loop's existing UTC convention
   instead (`queryIncentiveCostByUtcDay` in `finance-repository.ts`), rather than the reverse,
   because re-bucketing bookings was the option that was out of scope. The net result: the P&L is
   now internally consistent (every line buckets by the same UTC calendar day), but the whole P&L
   — not just the incentive line — deviates from spec §7.8's literal IST-day ask, and always has,
   for the booking side. `incentiveRepo.sumAppliedByIstDay` (Task 6) is left in place, correctly
   IST-bucketed, for any future IST-facing caller (e.g. the technician-facing week boundary, which
   is genuinely IST); it currently has no non-test caller. An accepted seam, not an oversight.

**Two further residuals from this build, briefly, because this ADR is the natural place a future
reader looks for known limitations of "incentives are credit-only and capped":**

- **The Semgrep static gate has a documented, tested residual gap for generic-wrapped type
  references** (`Promise<IncentiveAwardDoc>`, `IncentiveAwardDoc[]`, `IncentiveAwardDoc | null`).
  Task 17's round-2 fix closed the two gaps a real Semgrep run (via Docker; the native CLI is
  blocked in this environment) found in the round-1 rules — type-position references and
  object-literal property keys — but a bare generic-wrapper fragment was tested and found to
  silently match nothing rather than error, and was deliberately left uncovered rather than forced
  in. This gap is mitigated, not left bare: the independent `.strict()` write-schema gate (layer 1
  above) still throws at parse time regardless of what any static analysis tool does or does not
  catch in source, so a payout-shaped field cannot reach Cosmos even if it slips past Semgrep in a
  generic wrapper.
- **GitHub issue #340** was filed during Task 15's investigation for an unrelated admin-web bug:
  the owner P&L dashboard (`PnLChart.tsx`, `FinanceClient.tsx`) hard-codes the "profit" green for
  the net-to-owner figure regardless of sign, so a genuine loss day now renders identically to a
  profit day. This is out of scope for this ADR's own feature and lives in a separate sub-project,
  but it is worth a pointer here: it is `netToOwner`'s widening from `.nonnegative()` to `z.number()`
  in this same story (Task 15, correctly — read-path schemas only widen) that makes a negative P&L
  day reachable in production for the first time (an award-only day with no completed bookings
  produces a real negative net).

## Alternatives considered

- **A separate `technician_incentives` container** — rejected. It is superseded by architecture
  invariant #1 (one money container per technician partition) and invariant #10 (zero new
  containers); the ledger's `docType` discriminator already exists precisely to carry a new kind
  of financial document without a new container.
- **`markRemitted(..., 'ADJUSTMENT')`** — rejected. E21-S02 deleted that method entirely, and even
  if it still existed, mixing a bonus into remittance recording would destroy the P&L's
  distinction between commission the platform *forgave* (a remittance adjustment) and commission
  *settled by an incentive credit* (a cost the owner actually pays out in kind) — two different
  facts that a shared code path would conflate.
- **A `WAIVE` allocation type** — rejected for the same reason as above: `WAIVE` already means "the
  owner forgave this debt," which is a different fact from "the owner paid down this debt with an
  earned bonus." Reusing it would make the P&L's incentive-cost line indistinguishable from
  ordinary fee waivers.
