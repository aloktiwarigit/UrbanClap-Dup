# ADR-0020: Service-Area Polygon Gating in POST /v1/bookings

- **Status:** accepted
- **Date:** 2026-05-12
- **Deciders:** Alok Tiwari (owner), Claude (architect)
- **Story:** E16-S01
- **Threat-model row:** T-B1

## Context

The homeservices-mvp Phase 1 pilot is geographically limited to the Ayodhya region in Uttar Pradesh, India. Without server-side enforcement, any customer anywhere in India (or the world) can submit a `POST /v1/bookings` request with a spoofed or real `addressLatLng`, creating bookings that will never be fulfilled. This wastes dispatcher capacity, confuses technicians, and creates a poor customer experience when the booking eventually fails to be matched.

Additionally, the client-side lat/lng is a user-controlled value (submitted in the request body). It cannot be trusted. Server-side validation is mandatory.

**Binding constraints:**
- ₹0/month operational infra (rules out paid geofencing APIs like Mapbox, Google Maps Geofencing API)
- TypeScript + Node.js 22 + Azure Functions (ESM)
- The polygon will need to expand to Lucknow, Varanasi, and other cities in Phase 2

## Decision

We implement server-side service-area polygon gating in `POST /v1/bookings` using:

1. **Turf.js** (`@turf/boolean-point-in-polygon` + `@turf/helpers`) — OSS, MIT license, zero ongoing cost, runs in-process with no external API calls. Uses the ray-casting algorithm; boundary points are treated as inside (inclusive), satisfying AC-4.

2. **A GeoJSON Polygon feature** stored at `api/src/data/service-area-ayodhya.geojson` (canonical, for GIS tooling) and exported as a typed TypeScript constant from `api/src/data/service-area-ayodhya.ts` (for ESM import compatibility). The polygon is a 32-vertex regular polygon approximating a 25 km radius circle centered on Ramkot temple complex (Ram Janmabhoomi site) in Ayodhya.

3. **GrowthBook feature flag** `customer.service-area-gating.enabled` (default `false`) gating between:
   - **`false` (warn-only):** out-of-area coordinates are logged at INFO level (`service_area_check { inside: false, mode: "warn-only" }`) but the booking proceeds. Used during soak period.
   - **`true` (fail):** out-of-area coordinates return `400 { error: "SERVICE_NOT_AVAILABLE_AT_LOCATION", suggestedAction: "join_waitlist" }`.

4. **Zod input validation** on `LatLngSchema` adds `lat: z.number().min(-90).max(90)` and `lng: z.number().min(-180).max(180)` range guards so physically impossible coordinates are rejected at the schema layer (422 VALIDATION_ERROR) before reaching the polygon service.

### Polygon: Ayodhya 25 km radius

**Centre:** 26.7958°N, 82.1947°E (Ramkot / Ram Janmabhoomi area)

**Source:** Wikipedia "Ayodhya" article (https://en.wikipedia.org/wiki/Ayodhya) and Google Maps landmark pin for Ram Janmabhoomi temple complex. Cross-verified against Uttar Pradesh government mapping records for Faizabad (now Ayodhya) district.

**Radius:** 25 km (upper bound). Ayodhya city core is ~5 km across; the 25 km radius also covers Faizabad city and surrounding villages in the Ambedkar Nagar / Barabanki / Gonda border area.

**Vertex count:** 32 (GeoJSON ring has 33 coordinates — first and last are identical per the GeoJSON Polygon ring-closure rule).

**Generated by:** spherical destination-point formula (Vincenty-lite) at 0-degree bearing intervals of 360°/32 = 11.25°.

### Phase-2 Expansion Playbook

When expanding to Lucknow, Varanasi, Gorakhpur, or other cities:

1. **Add a new city polygon** to `api/src/data/service-areas.ts` (a new module that exports a named array or record of polygons). Each polygon is a `Feature<Polygon>` following the same 25 km / 32-vertex pattern (or a tighter hand-drawn polygon if GIS data is available).

2. **Update `service-area.service.ts`** to accept an array of polygons and run a union check (`polygons.some(p => isLatLngInServiceArea(lat, lng, p))`). The function signature stays compatible since it accepts `Feature<Polygon>`.

3. **Optionally add serviceability partitioning:** each polygon can carry a `properties.serviceIds: string[]` field so that a customer in Lucknow can only book services that have verified technicians in Lucknow. The gating logic then becomes: `isLatLngInAnyPolygon(lat, lng) && polygonForPoint(lat, lng).serviceIds.includes(serviceId)`.

4. **Keep the flag** `customer.service-area-gating.enabled` as the rollout gate. Set to `false` in a new city first; flip to `true` once ≥2 verified techs per active service are confirmed in that city.

5. **Polygon refinement:** for tight urban boundaries, replace the radius approximation with a hand-drawn polygon following actual tehsil/panchayat or municipal corporation boundaries. Export from GIS tooling as a valid GeoJSON Feature, validate the ring closure in a unit test.

## Consequences

- **Positive:** Physical impossibility for customers outside Ayodhya (25 km radius) to create bookings once the flag is flipped to `true`. Eliminates ghost bookings. Zero ongoing cost (OSS + in-process computation).
- **Positive:** Structured logging at INFO level provides a reconnaissance signal: >5 rejections/min/customer is an anomaly (threat-model T-B1).
- **Positive:** Fail-open GrowthBook flag design allows soak period (warn-only first week) before hard enforcement, reducing risk of false-positive rejections of legitimate Ayodhya customers.
- **Negative:** The 25 km radius is broader than strictly necessary — covers Faizabad city and surrounding villages. May generate customer confusion ("why can't I book from Gonda?" when Gonda is just outside 25 km). Mitigated by clear error message + `suggestedAction: "join_waitlist"`.
- **Negative:** Turf.js adds ~6 new transitive dependencies. Bundle size impact is negligible for Azure Functions (server-side only, no client bundle).
- **Neutral:** GeoJSON polygon is a static approximation. Exact boundaries can drift from reality (e.g. new colonies or municipal expansions). Acceptable for Phase 1 pilot.

## Alternatives Considered

- **Google Maps Geofencing API** — Paid ($0.002/check after free tier); violates ₹0 infra constraint. Rejected.
- **Mapbox Boundary API** — Paid. Rejected.
- **Client-side check only** — Trivially bypassable by spoofing lat/lng in the request body. The threat-model explicitly calls this out as T-B1. Rejected — server-side is mandatory.
- **IP geolocation** — VPNs bypass it; unreliable for mobile clients. Doesn't work for the trust boundary we need (physical location at service address). Rejected.
- **Full Turf.js bundle (`@turf/turf`)** — Heavy (hundreds of KB); we only need `boolean-point-in-polygon` + `helpers`. Rejected in favour of modular packages.
- **PostGIS / Cosmos geospatial** — Cosmos DB Serverless has limited geospatial support; PostGIS requires a separate DB server. Both add complexity and cost beyond the ₹0 constraint. Rejected.
