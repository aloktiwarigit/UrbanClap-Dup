# 3. Session learnings carried forward — read before your first push

Everything from the 2026-09-11 handoff's §3 still applies (Codex is the authoritative gate, never
`git add -A`, never push to `main` directly, read-path schemas only widen, worktree-per-workstream,
`.codex-review-passed` is a rolling marker on `main` — read its `commit` field, never its existence).
New from this session, worth carrying forward:

- **A CI job's own post-deploy health check can false-negative on a genuinely successful deploy.**
  `api-ship.yml`'s `Deploy to Azure Functions` job went red on "Verify health endpoint" while the
  actual deploy (steps 1–12, including "List indexed functions") had already succeeded. The
  `/api/v1/health` endpoint kept reporting the *previous* deployed commit for 6+ minutes (36 retries)
  after a genuinely successful Oryx remote-build deploy. **Don't trust the health-stamp check or the
  job conclusion** — verify by calling a new endpoint the story actually added
  (`GET /api/v1/technicians/me/incentives` returned a real `401 UNAUTHORIZED` from the new handler,
  not a gateway 404) and by checking `az functionapp function list` for the new function names. If
  the stamp is still stale after independent verification, `az functionapp restart` settles it —
  confirmed working, health correctly reported the new commit within 45 seconds of restart.
- **`api-ship.yml`'s deploy step itself is the documented anti-pattern.** It runs
  `func azure functionapp publish --javascript --build remote`, not the zip → blob →
  `WEBSITE_RUN_FROM_PACKAGE` method the project's own runbook calls correct (the Oryx remote-build
  variant sidesteps the Windows-`node_modules` failure mode since it builds on Linux CI, so it isn't
  currently causing harm — but it's still not the sanctioned method, and its health-check step is the
  unreliable one described above). Flagged, not fixed — raise it as its own story before another
  session sinks verification time into the same false-negative.
- **A branch built before a same-day merge train will have a stale generated OpenAPI client.**
  E23-S01 branched before #341/#342 landed; `api/openapi.json` was already current (no rebuild
  needed) but `admin-web/src/api/generated/{openapi.json,schema.d.ts}` weren't, and CI's
  `quality-gate` caught it (`admin-web/src/api/generated/ is stale`). Fixed by merging `main` into
  the branch **first**, then `pnpm run openapi:client` — confirmed forward-only (path count grew,
  nothing stripped) before committing. Regenerating from a stale base does the opposite: rewrites the
  client backwards and silently drops newer endpoints. This is now the second time this exact trap
  has cost a review round — check for it before pushing any branch that's more than a day old.
- **A worktree's HEAD can move while you're mid-verification if its owning session is still alive.**
  `wt-e23-s01`'s HEAD changed between two checks a few tool-calls apart (a docs-only commit landed
  from the session that built it). Always re-check `ListAgents` for the branch's originating session
  before treating a worktree's state as settled, and re-read HEAD right before you act on it, not
  just once at the start.
- **A background task's wrapper exit code is not the command's exit code.** `cmd > log 2>&1; echo
  EXIT:$? >> log` reports the `echo`'s exit code, not the piped command's, if you don't check `$?`
  from the *right* command. Caught a genuinely-failed web smoke gate (missing `node_modules`, exit
  127) that a `run_in_background` notification had reported as "completed exit code 0." Always grep
  the log's own content (`PASSED`, `Test Files`, `FAIL`) — never trust a wrapper's reported exit code
  or a notification summary.
