# E11-S05b-2 — Customer-app SOS Audio Truth-Up (Encrypted)

**Tier:** Foundation | **Security:** true | **Deps:** existing SOS (E11-S05b-1, already merged)

This story closes the truth-up gap on the SOS feature: today the customer-app records audio
to a local tmp file (`sos-{bookingId}.m4a`) and never uploads it. The PRD requires "encrypted
on device, uploaded to Storage, 7-day TTL" and an admin playback flow. This plan adds the
client-side AES-GCM encryption, Firebase Storage upload, key-doc API, admin playback endpoint,
and trims PII out of the existing owner FCM alert. Design is **fully locked** in the
brainstorm spec — see
`docs/superpowers/specs/2026-05-16-week5-foundation-stories-design.md` §1 — this plan only
translates it into work streams.

- `docs/patterns/paparazzi-cross-os-goldens.md` — any new or modified Paparazzi test must be

  ViewModel manually (no Hilt). New `SosAudioCipher` is injected as a plain class; in tests

- `docs/patterns/kotlin-explicit-api-public-modifier.md` — every new top-level Kotlin

## Architecture overview

**Encryption scheme.** Audio is encrypted client-side with AES/GCM/NoPadding (256-bit key,
96-bit IV, 128-bit authentication tag) via `javax.crypto.Cipher`. The key is generated per
incident with `KeyGenerator.getInstance("AES")`; the IV is generated with `SecureRandom` and
prepended to the ciphertext for storage. The plaintext `.m4a` file is wiped after encryption
succeeds so it never leaves `filesDir/sos/` even if the upload fails. The encrypted blob is
uploaded to Firebase Storage at `sos-audio/{customerId}/{incidentId}.enc`; Storage rules allow
writes only by the matching authenticated `uid` and reads only by admin custom-claim. A
Firebase Storage lifecycle rule deletes objects in the `sos-audio/` prefix 7 days after
creation (operationally configured — tracked in the runbook, not in code).

**Key-doc transport.** Once the upload succeeds the customer-app POSTs the AES key + IV
(Base64) to `POST /v1/sos/{incidentId}/key`. The API writes a `sos_incident_keys` Cosmos doc
(`/customerId` partition key, document-level TTL = 604_800s / 7 days). Cosmos default at-rest
encryption protects the key. There is no plaintext audio anywhere on our infra — neither the
blob nor the key alone is sufficient to decrypt.

**Admin playback.** A new admin endpoint
`GET /v1/admin/sos/{incidentId}/playback-token` (admin role: `OPERATIONS_LEAD` or
`SECURITY_OFFICER`, TOTP-fresh session) returns
`{ signedStorageUrl (V4 signed, 5-min TTL), keyB64, ivB64 }`. The admin-web client decrypts
in-browser via `crypto.subtle.decrypt({ name: 'AES-GCM', iv })` and streams to an HTML
`<audio>` element. Audio is never persisted plaintext on our infra. (Admin-web playback UI
is admin-side work; this plan stops at the endpoint.)

**FCM PII trim.** The existing `sendOwnerSosAlert` FCM payload carries `slotAddress` in the
data dict broadcast to the `owner_alerts` topic. FCM topic payloads are not end-to-end
encrypted — anyone subscribed to the topic on a compromised admin device gets the address.
This story drops `slotAddress` from the FCM payload; admin-web fetches the full incident
details via an authenticated `GET /v1/admin/sos/{incidentId}` call when the alert lands.

## Security invariants

- **Plaintext audio never persists beyond the encrypt step.** Tmp `.m4a` file is deleted
  after encrypt; the in-memory `ByteArray` is overwritten with zeros before being released.
- **The AES key is never written to disk client-side.** Key + IV live only on the JVM heap
  for the duration of the upload, then are sent to the API and discarded.
- **The encrypted blob and the key live in different services** (Firebase Storage vs Cosmos).
  An attacker compromising one must compromise the other to recover plaintext.
- **`sos_incident_keys` Cosmos doc readable only by admin-role JWT.** The customer-app's
  POST endpoint writes only; there is no customer-side read.
- **`GET /v1/admin/sos/{incidentId}/playback-token` requires TOTP-fresh session.**
  Re-authentication within the past 5 min via `requireFreshTotp` middleware (existing pattern
  in `api/src/middleware/`).
- **FCM topic payload for `SOS_ALERT` contains no PII** — only `bookingId`, `customerId`,
  `technicianId`, `incidentId`. Address resolution requires an authenticated round-trip.
- **Storage rule reads gated by admin custom-claim**, never by path-guessability. Writes
  gated by `request.auth.uid == {customerUid}` extracted from path segment.
- **Feature flag default off.** `customer.sos-audio-upload.enabled = false` until Week 5
  exit; the existing SOS countdown + FCM-only alert keeps working when the flag is off.

## Work streams

### WS-A — API: `sos_incident_keys` container + `POST /v1/sos/{incidentId}/key`

**New files:**
- `api/src/schemas/sos.ts` — Zod schemas:
  ```ts
  export const SosIncidentKeyDoc = z.object({
    id: z.string().min(1),               // incidentId == bookingId (1:1 per SOS today)
    customerId: z.string().min(1),
    keyB64: z.string().regex(BASE64_RE),  // 44-char base64 of 32-byte AES key
    ivB64: z.string().regex(BASE64_RE),   // 16-char base64 of 12-byte IV
    storagePath: z.string().regex(/^sos-audio\/[^/]+\/[^/]+\.enc$/),
    createdAt: z.string().datetime(),
    ttl: z.number().int().positive(),     // Cosmos TTL field, set to 604800 (7d)
  });
  export const SosKeyUploadRequest = SosIncidentKeyDoc
    .pick({ keyB64: true, ivB64: true, storagePath: true });
  ```
- `api/src/cosmos/sos-incident-key-repository.ts` — `putKeyDoc(doc)`, `getKeyDoc(incidentId,
  customerId)`. Partition: `/customerId`. Provision via `infra/cosmos/containers.ts`
  bootstrap with `defaultTtl: 604800` so all docs auto-delete after 7 days.
- `api/src/functions/sos-key.ts` — `POST /v1/sos/{incidentId}/key` handler:
  1. `requireCustomer` middleware (existing).
  2. Look up booking; 404 if missing, 403 if `booking.customerId !== customer.customerId`.
  3. **Require `booking.sosActivatedAt` to be set** — you cannot upload a key for an
     incident that was never triggered. Returns 409 `SOS_NOT_ACTIVATED` otherwise.
  4. `storagePath` in the request body must equal
     `sos-audio/{customer.customerId}/{incidentId}.enc` — server constructs the canonical
     path and rejects mismatches with 422.
  5. Idempotent write: if a key doc already exists for this `incidentId`, return 200
     `ALREADY_PROCESSED`; do not overwrite (prevents an attacker with the customer's JWT
     from rotating the key away from the original audio).
  6. Append audit log entry `SOS_KEY_UPLOADED` with `{ incidentId, storagePath }`.

### WS-D — Customer-app: `SosAudioCipher` helper

**New file:**
`customer-app/app/src/main/kotlin/com/homeservices/customer/data/sos/SosAudioCipher.kt`

```kotlin
public data class EncryptedBlob(
    public val ciphertext: ByteArray,
    public val keyB64: String,
    public val ivB64: String,
)

public class SosAudioCipher @Inject constructor() {
    public fun encrypt(plaintext: ByteArray): EncryptedBlob { … }
}
```

Implementation:
- Generate key: `KeyGenerator.getInstance("AES").apply { init(256) }.generateKey()`.
- Generate IV: 12 random bytes from `SecureRandom`.
- `Cipher.getInstance("AES/GCM/NoPadding")` + `GCMParameterSpec(128, iv)`.
- `doFinal(plaintext)` returns ciphertext+tag (GCM appends the 16-byte tag).
- Base64-encode key and IV using `android.util.Base64.NO_WRAP` — or
  `java.util.Base64.getEncoder()` (pure JVM, avoids needing Robolectric for the unit test).
  **Choose `java.util.Base64` for testability.**
- After encoding, zero out the plaintext `ByteArray` via `plaintext.fill(0)` in the caller
  (not in the cipher — the caller owns the buffer's lifetime).

**TDD:** `customer-app/app/src/test/kotlin/com/homeservices/customer/data/sos/SosAudioCipherTest.kt`
(pure JVM, no Robolectric):
- `encrypt_then_decrypt_roundtrip_matches_original_bytes` — decrypt with the same key+IV
  recovers the original plaintext.
- `each_invocation_produces_unique_key_and_iv` — two encrypts of the same plaintext yield
  different keys AND different IVs AND different ciphertexts.
- `ciphertext_length_equals_plaintext_length_plus_16_byte_tag` — verifies GCM tag included.

### WS-E — Customer-app: `SosAudioUploader` + `SosViewModel` extension

**New file:**
`customer-app/app/src/main/kotlin/com/homeservices/customer/data/sos/SosAudioUploader.kt`

```kotlin
public sealed interface SosUploadProgress {
    public data class Progress(public val pct: Int) : SosUploadProgress
    public object Success : SosUploadProgress
    public data class Failure(public val cause: Throwable) : SosUploadProgress
}

public class SosAudioUploader @Inject constructor(
    private val storage: FirebaseStorage,
    private val sosApi: SosApi,                  // existing Retrofit/Ktor interface — extend
    private val cipher: SosAudioCipher,
) {
    public fun upload(
        customerId: String,
        incidentId: String,
        plaintextAudio: ByteArray,
    ): Flow<SosUploadProgress> = callbackFlow {
        val encrypted = cipher.encrypt(plaintextAudio)
        plaintextAudio.fill(0)
        val path = "sos-audio/$customerId/$incidentId.enc"
        val task = storage.reference.child(path).putBytes(encrypted.ciphertext)
        task.addOnProgressListener { trySend(Progress(((it.bytesTransferred * 100) / it.totalByteCount).toInt())) }
        task.addOnFailureListener { trySend(Failure(it)); close() }
        task.addOnSuccessListener {
            launch {
                runCatching {
                    sosApi.uploadKey(incidentId, SosKeyUploadRequest(encrypted.keyB64, encrypted.ivB64, path))
                }.fold(
                    onSuccess = { trySend(Success); close() },
                    onFailure = { trySend(Failure(it)); close() },
                )
            }
        }
        awaitClose { if (!task.isComplete) task.cancel() }
    }
}
```

Citing `docs/patterns/firebase-callbackflow-lifecycle.md`: `awaitClose { task.cancel() }`
is what makes cancellation of the SosViewModel scope tear down the upload cleanly.

**Modify:** `customer-app/app/src/main/kotlin/com/homeservices/customer/ui/tracking/SosViewModel.kt`

`fireSos()` becomes:
```kotlin
private suspend fun fireSos() {
    val result = sosUseCase.execute(bookingId)
    if (!result.isSuccess) { _sosUiState.value = SosError(...); return }
    _sosUiState.value = SosConfirmed
    if (!featureFlags.isEnabled("customer.sos-audio-upload.enabled")) return
    val file = File(File(context.filesDir, "sos"), "sos-$bookingId.m4a")
    if (!file.exists()) return  // audio consent denied or recording failed
    val bytes = file.readBytes()
    file.delete()  // wipe plaintext before upload starts
    audioUploader.upload(customerId = sessionManager.customerId, incidentId = bookingId, plaintextAudio = bytes)
        .collect { progress ->
            _sosUiState.value = when (progress) {
                is Progress -> UploadingEvidence(progress.pct)
                is Success -> EvidenceSaved
                is Failure -> EvidenceUploadError(progress.cause.message ?: "upload_failed")
            }
        }
}
```

### WS-F — Firebase Storage rules + 7-day TTL lifecycle

**Modify:** `firebase/storage.rules` — append a new `match` block:

```javascript
// SOS audio — customer writes encrypted blob; admin reads via signed URL only
// (admin custom-claim required for direct read; lifecycle deletes after 7 days).
match /sos-audio/{customerId}/{incidentId}.enc {
  allow write: if request.auth != null
```

## Threat-model addendum

The PR appends to `docs/threat-model.md`:

- **S-A1 (FCM topic spoofing — owner alerts):** mark mitigated. Payload now contains no PII;
  even a topic-subscribing impostor learns only opaque IDs.
- **I-A2 (information disclosure — SOS slot address in FCM):** mark mitigated. `slotAddress`

- **NEW row — I-A4 (information disclosure — SOS key doc):** mitigation = Cosmos default

## ADR-0024

The PR creates `docs/adr/0024-sos-audio-e2e-encryption.md`, lifting content from
`docs/superpowers/specs/2026-05-16-week5-foundation-stories-design.md` §1. Sections:

- **Status:** Accepted (2026-05-16)
- **Context:** PRD requires SOS audio "encrypted on device"; FCM topic payload leaks PII.
- **Decision:** AES/GCM/NoPadding 256-bit; per-incident random key; IV prepended to
  ciphertext; key doc in `sos_incident_keys` Cosmos container (7d TTL); blob in
  `sos-audio/{customerId}/{incidentId}.enc` Firebase Storage (7d lifecycle); admin playback
  via signed URL + key bundle behind TOTP-fresh `requireAdmin` gate.
- **Consequences:** Pro — no plaintext audio on our infra; key+blob siloed across services.
  Con — admin playback requires WebCrypto JS decryption in admin-web (~50 LOC). Storage
  costs negligible (10 MB cap × 5k SOS/yr = ~50 GB/yr; well inside free tier with 7-day
  TTL).
- **Alternatives rejected:** Server-side encryption only (FAILS the "encrypted on device"
  PRD line); forensic-only (no admin playback — flagged in spec §1 as the owner-decision
  fallback, deferrable to a follow-up ADR if owner reverses course).
