# E17-S02 — Periodic 30s Technician Location Push (cross-app)

**Tier:** Foundation cross-app | **Security:** true | **Deps:** E11-S01b-1 (FCM router on customer-app) | **Blocks:** W6 E17-S03 (stale-data heartbeat)

This story spans three apps. Tech-app emits 30 s location samples from a foreground service, API persists + fans out via FCM, customer-app receives the data message and surfaces it to `LiveTrackingViewModel`. All design decisions are LOCKED in `docs/superpowers/specs/2026-05-16-week5-foundation-stories-design.md` §2 — this plan only translates the decisions into work streams.

## Architecture overview

```
┌─────────────────────────┐   30s tick    ┌──────────────────────────────────────┐
│ technician-app          │ ───POST────▶  │ API                                  │
│ LocationForegroundSvc   │               │ POST /v1/technicians/active-job/     │
│  ├─ FusedLocationCb     │               │      {bookingId}/location            │
│  ├─ callbackFlow        │               │  ├─ verifyTechnicianToken            │
│  └─ ActiveJobRepo       │               │  ├─ booking.technicianId === auth.uid│
│       observer wires    │               │  ├─ rate-limit (1/15s per tech+bkg)  │
│       start/stop on     │               │  ├─ Cosmos upsert(live_locations)    │
│       status changes    │               │  └─ FCM data → customer_{custId}     │
└─────────────────────────┘               └────────────────────┬─────────────────┘
                                                               │ topic
                                                               ▼
                                       ┌─────────────────────────────────────────┐
                                       │ customer-app                            │
                                       │ CustomerFirebaseMessagingService        │
                                       │   ├─ data["type"] == "LOCATION_UPDATE"  │
                                       │   └─ LocationUpdateEventBus.post(event) │
                                       │ LiveTrackingViewModel collects bus →    │
                                       │   exposes LocationState(lat,lng,ts)     │
                                       └─────────────────────────────────────────┘
```

Three failure boundaries:

1. **Tech-app foreground service drops samples** → no upstream effect; next 30 s tick covers it. `setMinUpdateDistanceMeters(15f)` is the explicit suppressor for an idle technician.
2. **API rate limit trips (429)** → tech-app logs warn and retries on the next tick. Cosmos write is skipped (the limit fires before the write).
3. **FCM publish fails** → server has already written Cosmos, so admin observability sees the latest fix. Customer just misses one tick; E17-S03 (W6) will add a heartbeat watchdog.

`LiveLocationDoc` in Cosmos has TTL = 3600 s (1 h), so we never accumulate stale rows past one job. The container is partitioned by `/bookingId`; reads are single-partition.

## Security invariants

- **Auth — assigned-tech-only.** The endpoint loads the booking and rejects with 403 if `booking.technicianId !== auth.uid`. A second tech cannot push for someone else's job.
- **Auth — booking status gate.** Only `EN_ROUTE | REACHED | IN_PROGRESS` are accepted; any other status returns 409 `BOOKING_NOT_ACTIVE`. Prevents stale clients from pushing after `COMPLETED`/`CANCELLED`.
- **Rate limit — D-L1 mitigation.** `1 request per 15 s per (techId, bookingId)` via the existing token-bucket middleware pattern, but keyed `rl:loc:{techId}:{bookingId}` instead of `rl:ip:{ip}`. 429 + `Retry-After` on exceed. Fail-open on Cosmos throttle as the existing middleware already does.
- **Payload — no PII on FCM topic.** FCM data message carries ONLY `{ type, bookingId, lat, lng, capturedAt }`. No technician name, photo URL, phone, or address — that data stays in Cosmos and is fetched via the authenticated tracking endpoints. (E13-S03 cleared the existing `LOCATION_UPDATE` payload of address; this plan keeps the same minimal shape.)
- **Capture freshness — replay protection.** `capturedAt` (ms since epoch) must be within ±90 s of server time; otherwise 400 `STALE_FIX`. Stops a captured packet from being replayed minutes later to alter the customer's view of the tech's position.
- **Permission posture — tech-app only.** `FOREGROUND_SERVICE_LOCATION` is declared in `technician-app/AndroidManifest.xml` only. Customer-app does not gain any new permission.
- **Kill switch.** GrowthBook flag `customer.periodic-location.enabled` (default off). When off, server still writes to Cosmos (admin keeps observability) but skips the FCM publish — customers see no live pin even if a rogue tech client is pushing.
- **Mock-fix flagging.** The tech-app captures `Location.isMock`/`isFromMockProvider` and forwards it as `attestation.isMock`; server logs a Sentry warning when true but allows the write through (matches existing `transitionStatus` behavior).

Handler outline:

```ts
const innerHandler: HttpHandler = async (req, ctx) => {
  // 1. verifyTechnicianToken → uid
  // 2. Parse bookingId from route params
  // 3. await bookingRepo.getById(bookingId) → 404 if missing
  // 4. booking.technicianId !== uid → 403
  // 5. booking.status ∉ {EN_ROUTE, REACHED, IN_PROGRESS} → 409 BOOKING_NOT_ACTIVE

  // 8. Build LiveLocationDoc; await liveLocationRepo.upsert(doc)
  // 9. if await featureFlags.isPeriodicLocationEnabled(booking.customerId)
  //      await sendPeriodicLocationPush(...).catch(ctx.error)
  // 10. return 204 (no body — successful publish has nothing to say)
};

export const activeJobLocationHandler =
  withRateLimit({
    keyExtractor: (req, uid) => `rl:loc:${uid}:${req.params.bookingId}`,
    buckets: { default: { capacity: 1, refillPerSec: 1/15 } },
  })(innerHandler);

app.http('activeJobLocation', {
  route: 'v1/technicians/active-job/{bookingId}/location',
  methods: ['POST'],
  authLevel: 'anonymous',
```

### WS-F — `LocationForegroundService`

**New file:** `technician-app/app/src/main/kotlin/com/homeservices/technician/data/location/service/LocationForegroundService.kt`

**Note on the existing `ActiveJobForegroundService`:** that service handles outbox sync and posts a generic "active job" notification with a low-importance channel `active_job_service`. It does NOT request periodic location updates. We deliberately do not extend it — adding a 30 s location-callback inside it would couple network-sync responsibility to GPS responsibility. Instead, this story adds a sibling service. Both can run concurrently while a job is active (Android allows multiple foreground services per app provided each declares the right `foregroundServiceType`).

Service shape:

```kotlin
@AndroidEntryPoint
public class LocationForegroundService : Service() {
    @Inject public lateinit var api: ActiveJobApiService
    @Inject public lateinit var locationProvider: FusedLocationProviderClient   // via LocationModule
    @Inject public lateinit var authTokenProvider: AuthTokenProvider             // existing

    private val serviceScope = CoroutineScope(SupervisorJob() + Dispatchers.IO)
    private var currentBookingId: String? = null
    private var callback: LocationCallback? = null

    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val bookingId = intent?.getStringExtra(EXTRA_BOOKING_ID) ?: return START_NOT_STICKY
        if (currentBookingId == bookingId) return START_STICKY   // idempotent re-start
        currentBookingId = bookingId
        createNotificationChannel()
        startForeground(NOTIFICATION_ID, buildNotification(bookingId),
            ServiceInfo.FOREGROUND_SERVICE_TYPE_LOCATION)
        startLocationUpdates(bookingId)
        return START_STICKY
    }

    private fun startLocationUpdates(bookingId: String) {
        val request = LocationRequest.Builder(30_000L)
            .setPriority(Priority.PRIORITY_BALANCED_POWER_ACCURACY)
            .setMinUpdateDistanceMeters(15f)
            .build()
        callback = object : LocationCallback() {
            override fun onLocationResult(result: LocationResult) {
                val loc = result.lastLocation ?: return
                serviceScope.launch { pushLocation(bookingId, loc) }
            }
        }
        // Permission check guarded — see WS-G LocationPermissionHelper.
        runCatching {
            locationProvider.requestLocationUpdates(request, callback!!, Looper.getMainLooper())
        }
    }

    private suspend fun pushLocation(bookingId: String, loc: Location) {
        runCatching {
            api.postActiveJobLocation(bookingId,
                PostLocationRequest(
                    lat = loc.latitude, lng = loc.longitude,
                    accuracyMeters = loc.accuracy.toDouble(),
                    capturedAt = loc.time,
                    attestation = LocationAttestationDto(
                        isMock = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) loc.isMock else loc.isFromMockProvider,
                        gpsAccuracyM = loc.accuracy,
                    ),
                ),
            )
        }.onFailure { Sentry.captureException(it) }
    }

    public override fun onDestroy() {
        callback?.let { locationProvider.removeLocationUpdates(it) }
        callback = null
        serviceScope.cancel()
        super.onDestroy()
    }

    override fun onBind(intent: Intent?): IBinder? = null

    public companion object {
        public const val CHANNEL_ID: String = "active_job_location"
        public const val EXTRA_BOOKING_ID: String = "bookingId"
        private const val NOTIFICATION_ID: Int = 2002

        public fun startIfNeeded(context: Context, bookingId: String) {
            if (!LocationPermissionHelper.hasForegroundLocation(context)) return
            val intent = Intent(context, LocationForegroundService::class.java)
                .putExtra(EXTRA_BOOKING_ID, bookingId)
            ContextCompat.startForegroundService(context, intent)
        }

        public fun stop(context: Context) {
            context.stopService(Intent(context, LocationForegroundService::class.java))
        }
    }
}
```

Notification copy is taken straight from the design spec:

| Lang | Title | Body |
|---|---|---|
| EN | Sharing location with customer | Only during active booking |
| HI | ग्राहक के साथ स्थान साझा कर रहे हैं | केवल सक्रिय बुकिंग के दौरान |

Channel `CHANNEL_ACTIVE_JOB_LOCATION` is `IMPORTANCE_LOW`, no sound, no vibration. Tap action: `Intent(ACTION_VIEW)` with `homeservices://action/active-job/{bookingId}` so `MainActivity`'s existing deep-link receiver (see manifest) routes to the active-job screen.

### WS-H — State-machine integration

The repository already exposes `activeJobState: StateFlow<ActiveJob?>` (see `ActiveJobRepositoryImpl`). Status transitions flow through this StateFlow on every `transitionStatus` call. We add a single observer that maps status → service control.

**New file:** `technician-app/app/src/main/kotlin/com/homeservices/technician/data/activeJob/ActiveJobLocationObserver.kt`

```kotlin
@Singleton
public class ActiveJobLocationObserver @Inject internal constructor(
    @ApplicationContext private val appContext: Context,
    private val repository: ActiveJobRepository,
) {
    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)

    public fun start() {
        scope.launch {
            repository.activeJobState.collect { job ->
                when (job?.status) {
                    ActiveJobStatus.EN_ROUTE,
                    ActiveJobStatus.REACHED,
                    ActiveJobStatus.IN_PROGRESS ->
                        LocationForegroundService.startIfNeeded(appContext, job.bookingId)
                    ActiveJobStatus.COMPLETED, null ->
                        LocationForegroundService.stop(appContext)
                    ActiveJobStatus.ASSIGNED -> Unit   // pre-trip, no push
                }
            }
        }
    }
}
```

Wire-up in `HomeservicesTechnicianApplication.onCreate`:

```kotlin
@Inject lateinit var activeJobLocationObserver: ActiveJobLocationObserver
// ...
activeJobLocationObserver.start()
```

**Recovery — process death:** the existing `BootReceiver` only handles boot-time pending-transition resume. Add a parallel recovery: on `Application.onCreate`, after `activeJobLocationObserver.start()` is wired, the observer immediately replays the current `activeJobState` value (StateFlow always emits its current value to a new collector). If the user has an in-progress booking persisted via `ActiveJobRepositoryImpl.startObserving` (called from `ActiveJobViewModel.init`), the service restarts as soon as the VM re-primes the state. For the case where the app is launched cold without entering the active-job screen, the observer remains idle — acceptable for the pilot, and matches `BootReceiver`'s narrow scope (it intentionally only resumes when there are pending Room transitions).

**Cancelled/no-show** are not Active-job statuses in the current `ActiveJobStatus` enum (they are bookings-level events handled by the no-show projector). The observer's `null` branch (when `activeJobState` clears or a booking is removed remotely via FCM `JOB_UPDATE`) doubles as the cancel/no-show stop signal — `LocationForegroundService.stop` is idempotent.

### WS-J — ViewModel integration

**Modify** `customer-app/.../ui/tracking/LiveTrackingViewModel.kt` and add a new `LocationState` source:

```kotlin
public data class LocationState(val lat: Double, val lng: Double, val capturedAt: Long)
```

Inject `LocationUpdateEventBus` and merge its filtered flow with the existing tracking combine:

```kotlin
@HiltViewModel
public class LiveTrackingViewModel @Inject constructor(
    savedStateHandle: SavedStateHandle,
    private val getLiveLocationUseCase: GetLiveLocationUseCase,
    private val trackBookingStatusUseCase: TrackBookingStatusUseCase,
    private val locationUpdateEventBus: LocationUpdateEventBus,
) : ViewModel() {
    private val bookingId: String = checkNotNull(savedStateHandle["bookingId"])

    private val liveLocationFromBus: StateFlow<LocationState?> =
        locationUpdateEventBus.events
            .filter { it.bookingId == bookingId }
            .map { LocationState(it.lat, it.lng, it.capturedAt) }
            .stateIn(viewModelScope, SharingStarted.Eagerly, null)

    public val uiState: StateFlow<LiveTrackingUiState> =
        combine(
            getLiveLocationUseCase.execute(bookingId),
            trackBookingStatusUseCase.execute(bookingId),
            liveLocationFromBus,
        ) { legacyLocation, status, busLocation ->
            // bus wins when present (slim payload is the canonical 30s pin).
            // legacyLocation still carries techName/photoUrl needed for the header.
            LiveTrackingUiState.Tracking(
                bookingId = bookingId,
                location = legacyLocation,
                status = status,
                techName = legacyLocation?.techName ?: "",
                techPhotoUrl = legacyLocation?.techPhotoUrl ?: "",
                etaMinutes = legacyLocation?.etaMinutes,
                technicianId = legacyLocation?.technicianId,
                liveLat = busLocation?.lat ?: legacyLocation?.lat,
                liveLng = busLocation?.lng ?: legacyLocation?.lng,
                liveCapturedAt = busLocation?.capturedAt,
            )
        }.stateIn(viewModelScope, SharingStarted.Eagerly, LiveTrackingUiState.Loading)
}
```

Add the three fields (`liveLat`, `liveLng`, `liveCapturedAt`) to `LiveTrackingUiState.Tracking`. The existing `LiveTrackingScreen` consumes `location.lat`/`location.lng` for the map marker today — switch it to prefer `liveLat`/`liveLng` when non-null. This is a 3-line change in the screen and does not require a Paparazzi golden update (no new composables, no layout change).

## ADR-0019 — Periodic technician location push

The PR creates `docs/adr/0019-periodic-tech-location.md`. Content sourced verbatim from spec §2; structure:

1. **Status:** Accepted, 2026-05-16.
2. **Context:** Customer needs sub-minute pin freshness during EN_ROUTE → IN_PROGRESS. WorkManager's 15-minute minimum is too coarse; persistent socket is paid SaaS.
3. **Decision:** Foreground service on tech-app (Channel `active_job_location`, `FOREGROUND_SERVICE_TYPE_LOCATION`), 30 s tick via `FusedLocationProviderClient` with `setMinUpdateDistanceMeters(15f)`. Server publishes via FCM data message gated by GrowthBook flag.
4. **Consequences:**
   - Pro: ₹0 infra (FCM unlimited), 30s freshness, idle suppression, kill-switch.
   - Pro: leverages existing `customer_{customerId}` topic — no new infrastructure.
   - Con: 2-3 %/hr battery on a 45-min job (acceptable per existing risk register).
   - Con: requires `FOREGROUND_SERVICE_LOCATION` runtime permission on Android 14+ (already declared).
5. **Alternatives rejected:**
   - WorkManager periodic — 15-min minimum cadence misses the requirement.
   - Persistent WebSocket — needs paid backend (violates ₹0 constraint).
   - Background service without notification — Android 14 disallows.
6. **Rollback:** flip `customer.periodic-location.enabled` to false → FCM publishes stop; Cosmos writes continue (admin observability remains).

The plan execution will write this ADR file. Do not pre-write it.
