## Architecture overview

The durable-hook contract (E11 spec §§1–4) applied to the technician dashboard:

```
FCM data message received
  │
  ├─► HomeservicesFcmService.handleMessageData(data)
  │     ├─► router.parseFcmData(data) → NotificationIntent (if recognised type)
  │     ├─► ingestor.ingest(action)   → Room upsert (version-aware, tombstone-safe)
  │     │     └─► IngestEvent emitted
  │     └─► tray notification (background) or IngestEvent banner (foreground)
  │
  └─► (new dashboard-relevant types) → handled inline if not yet in core-nav schema
        JOB_ASSIGNED, RATING_PROMPTED, EARNINGS_UPDATED are already routed by existing
        FCM branches; this story wires them into PendingActionStore for durability.

Dashboard screen (TechnicianHomeScreen) on resume / foreground:
  ├─► TechnicianDashboardViewModel.observePendingActions()
  │     ├─► PendingActionStore.observeActive(userId) [Room Flow]
  │     └─► merge with DashboardRepository.observe() [API poll]
  └─► Renders banners/cards for JOB_OFFER, JOB_ASSIGNED, RATING_PROMPT_TECHNICIAN,
      RATING_RECEIVED, EARNINGS_UPDATE pending actions

Cold start / onResume:
  ├─► PendingActionIngestor.reconcile(userId) ← GET /v1/technicians/me/pending-actions
  └─► TierLadder decides initial route; Dashboard is T6 default unless T2 active job present

App-start intent (deep-link tap from tray notification):
  └─► homeservices://action/<TYPE>?<args> → NotificationRouter.parseDeepLink → routeFor
```

**Screen consumes from Room on resume** — no event buses. Existing legacy buses
(`JobOfferEventBus`, `RatingPromptEventBus`, `EarningsUpdateEventBus`, `RatingReceivedEventBus`)
are preserved (not removed — that is E11-S01b-2 scope). The ViewModel observes Room in parallel
with the legacy bus signals so both paths work during the transition.

### WS-C — `TechnicianDashboardViewModel` + dashboard screen wiring

The `TechnicianHomeScreen` (in `ui/home/`) is the live, fully-wired dashboard used in production via
`HomeGraph`. The `TechnicianDashboardScreen` (in `ui/dashboard/`) is a static placeholder used by a
`HOME_DASHBOARD_ROUTE` composable via `homeGraph`. **Extend `TechnicianHomeScreen` / `TechnicianHomeViewModel`** — that is the real screen.

**C1: `TechnicianDashboardViewModel`** — new ViewModel (or extend `TechnicianHomeViewModel`; prefer
new class to keep blast radius small and avoid disrupting existing earnings/ratings flows).

```kotlin
@HiltViewModel
public class TechnicianDashboardViewModel @Inject constructor(
    private val pendingActionStore: PendingActionStore,
    private val sessionManager: SessionManager,     // for userId
) : ViewModel() {
    public val pendingActions: StateFlow<List<PendingAction>> = ...
    // observeActive filtered to dashboard-relevant types:
    // JOB_OFFER, JOB_ASSIGNED, RATING_PROMPT_TECHNICIAN, RATING_RECEIVED, EARNINGS_UPDATE
    // Priority order: HIGH first (JOB_OFFER), then NORMAL, then LOW
}
```

Filtered observe (inside `init`):
```kotlin
pendingActionStore.observeActive(userId)
    .map { list -> list.filter { it.type in DASHBOARD_ACTION_TYPES } }
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())
```

`DASHBOARD_ACTION_TYPES` = `setOf(JOB_OFFER, JOB_ASSIGNED, RATING_PROMPT_TECHNICIAN,
RATING_RECEIVED, EARNINGS_UPDATE)`.

**C2: Pending-action card composable** — `PendingActionCard.kt` (new, internal):
```kotlin
@Composable
internal fun PendingActionCard(
    action: PendingAction,
    onClick: (PendingAction) -> Unit,
    modifier: Modifier = Modifier,
)
```
Renders based on `action.type`:
- `JOB_OFFER` — amber accent, countdown chip if `expiresAt != null`, "₹X • Service • Distance" body.
- `JOB_ASSIGNED` — green accent, "Booking assigned — tap to open active job" body.
- `RATING_PROMPT_TECHNICIAN` — blue accent, "Rate this job" body.
- `RATING_RECEIVED` — purple accent, "You received a rating — view feedback" body.
- `EARNINGS_UPDATE` — teal accent, "Earnings updated — tap to view" body.

Uses `HsSectionCard` from design-system; accent via `MaterialTheme.colorScheme` tonal containers.

**C3: Wire into `TechnicianHomeScreen`**
Add `TechnicianDashboardViewModel` as a second `hiltViewModel()` call in `HomeDashboardRoute`
(or pass down from HomeGraph). Collect `pendingActions` state; render `PendingActionCard` items
above the existing job-list / availability sections.

OnClick routing for each card type:
- `JOB_OFFER` → navigate to job offer full-screen (`JobOfferFullScreenActivity` or existing offer route).
- `JOB_ASSIGNED` → navigate to `ActiveJobRoute(bookingId = action.entityId)`.
- `RATING_PROMPT_TECHNICIAN` → navigate to `RatingRoutes.route(action.entityId)`.
- `RATING_RECEIVED` → navigate to `ratings_transparency`.
- `EARNINGS_UPDATE` → navigate to `payout_settings` (or earnings screen).

**C4: `onResume` reconcile trigger**
Add `LaunchedEffect(Unit) { dashboardVm.reconcile() }` in `HomeDashboardRoute`. The
`TechnicianDashboardViewModel.reconcile()` method calls the (already-wired) `ingestor.reconcile(userId)`.
