## Architecture overview

### GET /v1/services/{id}/availability

```
Query param: date=YYYY-MM-DD (required; today ≤ date ≤ today+7)

Response 200:
{
  serviceId: string,
  date: string,          // YYYY-MM-DD echo
  slotGranularityMinutes: number,   // e.g. 60
  slots: Array<{
    window: string,      // "HH:MM-HH:MM"
    available: boolean
  }>
}
```

**Slot generation:** The service doc already stores `durationMinutes`. This story adds two
optional fields to the service doc (via catalogue admin, no schema migration required):
`workStart: "HH:MM"` (default `"08:00"`) and `workEnd: "HH:MM"` (default `"20:00"`).
Slots are generated server-side as `durationMinutes`-wide non-overlapping windows within
`[workStart, workEnd)`. For a 60-min service starting at 08:00 and ending at 20:00 the
windows are `08:00-09:00`, `09:00-10:00`, … `19:00-20:00` (12 slots).

**Unavailability detection:** A slot is marked `available: false` if either:
1. An unexpired `slot_holds` doc exists for `serviceId + date + window` (soft hold), OR
2. A `bookings` doc exists with `serviceId + slotDate + slotWindow` and status not in
   `{CUSTOMER_CANCELLED, UNFULFILLED}` (hard booking).

Bookings are queried by cross-partition scan on `(serviceId, slotDate)` — acceptable at
pilot scale (≤5,000 bookings/mo). Holds are a single-partition read on the composite
partition key `serviceId-date` (see WS-A).

### Slot holds + POST /v1/bookings extension

```
slot_holds container
  Partition key: /servicePartitionKey  ("serviceId|YYYY-MM-DD")
  Default TTL:    30 seconds  (soft-hold duration; see note below)
  Doc id:         "<serviceId>|<YYYY-MM-DD>|<HH:MM-HH:MM>"
```

**Hold lifecycle:**
1. `POST /v1/bookings` receives `slotDate` + `slotWindow` (already in schema — regex
   `/^\d{2}:\d{2}-\d{2}:\d{2}$/`; no new request fields needed).
2. Server calls `slotHoldsRepo.createHold(serviceId, date, window, customerId)`.
   - Cosmos `items.create()` with `{ id, servicePartitionKey, serviceId, date, window,
     customerId, heldAt: ISO }`. TTL inherited from container default (30 s).
   - If Cosmos returns **409** (doc already exists — another customer holds this slot) →
     return `{ status: 409, code: 'SLOT_UNAVAILABLE' }`. Booking creation aborts.
   - If Cosmos returns **412** (optimistic concurrency conflict on a concurrent upsert path,
     same fallback pattern as ADR-0017 §5) → same `SLOT_UNAVAILABLE` response.
3. On successful booking creation → `slotHoldsRepo.commitHold(id, bookingId)` writes
   `bookingId` into the hold doc and sets TTL to `-1` (no expiry). This converts the
   soft hold into a permanent booking-owned slot record.
   **Trade-off vs. deleting:** Keeping the committed hold avoids a race where availability
   is re-checked between hold deletion and booking write. Setting TTL to `-1` is a single
   Cosmos PATCH that is cheaper than delete + the booking's own slot lookup. The hold doc
   is effectively a denormalized "slot occupied" index.
4. If booking creation fails after hold write → hold expires naturally (30 s TTL) and the
   slot becomes available again. No compensating delete needed.

**30-second hold duration:** The roadmap specifies 30 s. This is a product decision: a
customer browsing from slot-pick to payment will typically complete in < 30 s on mobile.
If conversion data shows abandonment, extend to 120–300 s with a separate ADR. Longer
holds reduce throughput on popular slots — document this trade-off explicitly.

## Security invariants

- Caller must be an authenticated customer (Firebase ID token via `requireCustomer`
  middleware). Unauthenticated requests → 401.
- `serviceId` must resolve to an active service (`isActive = true`) in the catalogue
  container. Unknown / inactive service → 404.
- `date` must satisfy `today ≤ date ≤ today+7` (server-side check in UTC+5:30 IST, not
  UTC). Dates in the past or > 7 days out → 422 `INVALID_DATE_RANGE`.
- `slotWindow` in `POST /v1/bookings` is validated against the server-generated windows
  for that `serviceId + slotDate`. A fabricated window that doesn't align with generated
  slots → 422 `INVALID_SLOT_WINDOW`.
- Service-area polygon gating (ADR-0020 / E16-S01) remains in place upstream of slot logic.

### WS-B — Repository: `slot-holds-repository.ts`

New file: `api/src/cosmos/slot-holds-repository.ts`

**Key method signatures:**

```typescript
// Returns the created hold, or 'CONFLICT' if slot is already held/booked.
createHold(
  serviceId: string,
  date: string,
  window: string,
  customerId: string,
): Promise<SlotHoldDoc | 'CONFLICT'>

// Converts soft hold to committed (permanent). Call after booking write succeeds.
commitHold(holdId: string, servicePartitionKey: string, bookingId: string): Promise<void>

// Lists all active (non-expired) holds for a service+date partition.
listHolds(serviceId: string, date: string): Promise<SlotHoldDoc[]>
```

**`createHold` implementation detail:**
- Build `id = "${serviceId}|${date}|${window}"`.
- `servicePartitionKey = "${serviceId}|${date}"`.
- Call `container.items.create(doc, { consistencyLevel: 'Session' })`.
- Catch `ErrorResponse` with `statusCode === 409` → return `'CONFLICT'`.
- Catch `ErrorResponse` with `statusCode === 412` → return `'CONFLICT'` (same user-facing
  result; same pattern as ADR-0017 §5 `_etag` fallback).
- Any other error → rethrow (Sentry will capture upstream).

**`commitHold` implementation detail:**
- `container.item(holdId, servicePartitionKey).patch([
    { op: 'add', path: '/bookingId', value: bookingId },
    { op: 'replace', path: '/ttl', value: -1 },
  ])`
- If the hold has already expired (404) → log warning and return silently. The booking
  succeeded; the slot will be visible as booked via the `bookings` scan in `listHolds`.

**`listHolds`:** Query `SELECT * FROM c WHERE c.servicePartitionKey = @pk` — single-partition,
no cross-partition flag needed.

**TDD — WS-B (integration, use Cosmos emulator via Testcontainers or in-memory mock):**
- Happy path: `createHold` succeeds → doc exists in container.
- Conflict path: second `createHold` with same `serviceId + date + window` → returns
  `'CONFLICT'`.
- Expired hold path: hold with TTL=1 second; after 2 s `listHolds` returns empty array;
  third `createHold` on same slot succeeds.
- `commitHold` happy path: doc updated with `bookingId`, `ttl=-1`.
- `commitHold` on expired hold (404): no exception thrown.

### WS-C — Function: `GET /v1/services/{id}/availability`

New file: `api/src/functions/services-availability.ts`

**Route registration:**
```typescript
app.http('servicesAvailability', {
  methods: ['GET'],
  route: 'v1/services/{id}/availability',
  handler: requireCustomer(availabilityHandler),
});
```

**Handler logic:**

1. Zod-parse `id` from route params (min 1, `^[a-z0-9-]+$`).
2. Zod-parse `date` from query string: `z.string().regex(/^\d{4}-\d{2}-\d{2}$/)`.
3. Validate date range (today IST ≤ date ≤ today+7 IST). Return 422
   `INVALID_DATE_RANGE` if outside window.
4. `catalogueRepo.getServiceByIdCrossPartition(id)` — 404 if not found or `!isActive`.
5. Generate slots: `generateSlots(service, date)` (pure function, easily unit-tested).
   - `workStart = service.workStart ?? '08:00'`, `workEnd = service.workEnd ?? '20:00'`.
   - Walk from `workStart` in `service.durationMinutes` increments until `>= workEnd`.
   - Return array of `"HH:MM-HH:MM"` strings.
6. Load held windows: `slotHoldsRepo.listHolds(id, date)` → extract `window` strings.
7. Load booked windows: query `bookings` container cross-partition:
   ```sql
   SELECT c.slotWindow FROM c
   WHERE c.serviceId = @serviceId
     AND c.slotDate = @date
     AND c.status NOT IN ('CUSTOMER_CANCELLED', 'UNFULFILLED')
   ```
   Extract `slotWindow` strings.
8. Build unavailable set = union of held + booked windows.
9. Map generated slots to `{ window, available: !unavailableSet.has(window) }`.
10. Return 200 `AvailabilityResponse`.

**TDD — WS-C:**
- Happy path: service exists, date valid, no holds/bookings → all slots `available: true`.
- 422 for past date, 422 for date > today+7, 422 for malformed date `"2026-13-01"`.
- 404 for unknown serviceId, 404 for inactive service.
- Held slot → `available: false`. Hard-booked slot → `available: false`.
- Expired hold (TTL elapsed) → slot reappears as `available: true`.
- Non-cancelled booking on same slot → `available: false`.

### WS-D — Extend `POST /v1/bookings`: slot-hold gate

**File:** `api/src/functions/bookings.ts` (modify `createHandler`)

The `slotDate` and `slotWindow` fields are already in `CreateBookingRequestSchema` and
`BookingDocSchema`. No new request fields needed.

**Insert after** the service-area gating block and before `catalogueRepo.getServiceByIdCrossPartition`:

```typescript
// E16-S02: Slot-conflict locking — attempt to hold the slot before writing the booking.
// createHold returns 'CONFLICT' if another hold or booking already occupies this window.
const holdResult = await slotHoldsRepo.createHold(
  parsed.data.serviceId,
  parsed.data.slotDate,
  parsed.data.slotWindow,
  customer.customerId,
);
if (holdResult === 'CONFLICT') {
  return {
    status: 409,
    jsonBody: { code: 'SLOT_UNAVAILABLE', message: 'This time slot is no longer available.' },
  };
}
const holdId = holdResult.id;
const holdPk = holdResult.servicePartitionKey;
```

**After successful booking creation** (all three paths: cash, full-credit, Razorpay), add:

```typescript
// Commit hold — converts 30 s soft hold to permanent slot record.
slotHoldsRepo.commitHold(holdId, holdPk, booking.id).catch((err: unknown) => {
  // Non-fatal: if commit fails the slot hold expires in 30 s and becomes available again.
  // The booking itself is committed; this is a best-effort denormalization.
  Sentry.captureException(err);
  console.warn('[createBooking] commitHold failed (non-fatal)', { holdId, bookingId: booking.id, err });
});
```

**Validate slot window against service config:** Before the hold, verify the requested
`slotWindow` is one of the server-generated windows for that service + date. If not → 422
`INVALID_SLOT_WINDOW`. Reuse the `generateSlots` pure function from WS-C (extracted to
`api/src/shared/slot-utils.ts`).

**TDD — WS-D (unit, mock slotHoldsRepo):**
- `createHold` returns hold doc → booking proceeds normally.
- `createHold` returns `'CONFLICT'` → handler returns 409 `SLOT_UNAVAILABLE`.
- Invalid `slotWindow` not in generated slots → 422 `INVALID_SLOT_WINDOW`.
- `commitHold` rejects → Sentry captures; booking response still returned.

## ADR / threat-model notes

**Hold duration ADR trigger:** The 30-second hold is the default. If UX data shows customers
need > 30 s from slot-pick to payment confirmation (e.g. biometric + Razorpay round-trip),
the hold can be extended to 120–300 s by changing the container `defaultTtl`. A duration
> 300 s (5 min) meaningfully reduces throughput on popular slots and **requires a separate
ADR** documenting the trade-off before changing.

**Threat-model:** No new threat-model row required. Slot-spoofing (fabricated `slotWindow`
in `POST /v1/bookings`) is bounded by:
1. Server-side `generateSlots` validation (WS-D) — fabricated windows are rejected 422.
2. Service-area gating (T-B1, ADR-0020) remains upstream — location must be inside
   Ayodhya polygon before slot logic is reached.
3. The `slot_holds` doc id is deterministic on `serviceId + date + window`; a customer
   cannot hold a slot that isn't in the server-generated window list.

Karnataka invariant (ADR-0006/0011): Not affected. Slot locking does not touch dispatcher
ranking. Verified.
