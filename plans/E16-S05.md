## E16-S02 dependency note

`plans/E16-S02.md` was being authored in parallel at plan-write time. Based on the roadmap
(`docs/superpowers/plans/2026-05-12-customer-app-gap-closure-roadmap.md` §E16-S02):

- **Availability API shape:** `GET /v1/services/{id}/availability?date=YYYY-MM-DD`
  → `{ slots: [{ window: "HH:MM-HH:MM", available: Boolean }] }`
- **Soft-hold mechanic:** The roadmap defines a 30-second soft-hold on `POST /v1/bookings`, not a
  separate `PUT/POST /v1/slot-holds` call. There is **no explicit hold-creation endpoint on the
  slot-picker screen itself**, and the roadmap does not define a `DELETE /v1/slot-holds/{holdId}`
  release call.
- **Hold-release decision:** Rely on the 30-second Cosmos TTL auto-expiry rather than an explicit
  client-side `DELETE`. When the user presses Back before confirming, the soft-hold (if any) will
  naturally expire within 30 seconds. This avoids a round-trip on back-navigation and keeps the
  client stateless w.r.t. hold IDs.
  - If E16-S02 plan does define an explicit release endpoint (`DELETE /v1/slot-holds/{holdId}`),
    the implementer **must** add a `BackHandler` in `SlotPickerScreen` that calls
    `viewModel.releaseHold()` before invoking `onBack`. Add a corresponding
    `SlotPickerRepository.releaseHold(holdId)` method and a `holdId: String?` field to
    `SlotPickerUiState.Loaded`. This extension is scoped to WS-A / WS-B without touching WS-C.

## Architecture overview

```
SlotPickerScreen (Compose)
  └─ SlotPickerViewModel
       └─ GetSlotAvailabilityUseCase
            └─ SlotAvailabilityRepository (interface)
                 └─ SlotAvailabilityRepositoryImpl
                      └─ BookingApiService  (new endpoint added)
```

**State machine — `SlotPickerUiState`:**
- `Loading` — spinner shown
- `Loaded(date: LocalDate, slots: List<SlotWindow>)` — grid of morning/afternoon/evening chips
- `Error(message: String)` — retry button

**`SlotWindow`** (domain model):
```
data class SlotWindow(val window: String, val available: Boolean)
```

**Past-time filter (client-side):** Applied inside the ViewModel when `date == LocalDate.now()`.
A slot window is additionally filtered as unavailable if its start hour has already passed
(`LocalTime.now()` — no server clock dependency). The server is the authority on `available`;
the client only adds a stricter past-time overlay.

**Time-of-day bucketing (UI-only):**
- Morning: windows starting before 12:00
- Afternoon: 12:00–17:00
- Evening: 17:00+

Sections with zero available slots are hidden (collapsed), not shown empty.

**Confirm CTA:** enabled only when the user has selected an available slot. Calls
`onSlotSelected(BookingSlot(date, window))` — the existing `BookingViewModel.setSlotAndAddress`
signature is unchanged.

internal class SlotAvailabilityRepositoryImpl @Inject constructor(
    private val api: BookingApiService,
) : SlotAvailabilityRepository {
    override fun getAvailability(serviceId: String, date: LocalDate): Flow<Result<List<SlotWindow>>> =
        flow {
            emit(runCatching {
                api.getSlotAvailability(serviceId, date.format(DateTimeFormatter.ISO_LOCAL_DATE))
                    .slots.map { it.toDomain() }
            })
        }
}
```

public fun selectSlot(slot: SlotWindow)
public fun retry(serviceId: String, date: LocalDate)
```

**Past-time filter logic (inside `loadSlots`):**
```kotlin
val nowHour = LocalTime.now().hour
val filtered = slots.map { slot ->
    val slotStartHour = slot.window.substringBefore(":").toIntOrNull() ?: 0
    if (date == LocalDate.now() && slotStartHour <= nowHour) {
        slot.copy(available = false)
    } else {
        slot
    }
}
```
`filteredSlots` replaces the raw list in `Loaded` state for rendering. `selected` cleared if its
window becomes unavailable after a date change.

**Date change:** `loadSlots` is called with the newly chosen `date`; `selected` resets on each call.

### B3: Tests — `SlotPickerViewModelTest` (manual construction, no Hilt)
**New file:** `test/.../ui/booking/SlotPickerViewModelTest.kt`

Scenarios (use `TestCoroutineDispatcher` / `UnconfinedTestDispatcher`):
- `loadSlots` → transitions `Loading → Loaded` on success
- `loadSlots` → transitions `Loading → Error` on failure
- Past-time filter: today + slot start hour ≤ `LocalTime.now().hour` → `available = false`
- Past-time filter: future date → no slots overridden
- `selectSlot` → updates `Loaded.selected`
- `retry` → re-triggers load (Loaded state refreshed)
- Date change resets `selected` to null

## Summary

E16-S05 replaces the hard-coded `SlotPickerScreen` with an API-driven one. The plan adds a thin
domain layer (`SlotWindow`, `GetSlotAvailabilityUseCase`, `SlotAvailabilityRepository`) and a new
`SlotPickerViewModel` that calls the E16-S02 availability endpoint, applies client-side past-time
filtering, and exposes a `Loading/Loaded/Error` state to the Compose UI. The screen grids slots into
morning/afternoon/evening sections with unavailable chips greyed-out. Soft-hold release relies on the
30-second Cosmos TTL (no explicit `DELETE` call needed). Six `@Ignored` Paparazzi stubs replace the
two existing ones.
